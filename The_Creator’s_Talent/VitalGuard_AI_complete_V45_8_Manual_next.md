# VitalGuard 업데이트 매뉴얼 — V4.5.8 이후 미구현 개선 항목

이 문서는 다음 세션의 AI가 그대로 읽고 작업에 착수할 수 있도록 작성된 실행용 매뉴얼이다.
현재 최신 안정 파일은 `VitalGuard_AI_complete_V45_8.html`이며, 이 문서의 모든 항목은
그 파일을 기준으로 아직 구현되지 않은 상태이다. 각 항목은 무엇을 왜 어디를 어떻게
고치는지, 그리고 완료를 어떻게 검증하는지까지 포함한다.

---

## 0. 작업 시작 전 반드시 지켜야 하는 기본 규칙

이 규칙은 VitalGuard 프로젝트의 불변 원칙이다. 아래 항목을 위반하면 결과물을 폐기하고
다시 작업한다.

1. 바닐라 HTML과 바닐라 JS만 사용한다. 외부 라이브러리, CDN, npm 패키지, 프레임워크,
   외부 fetch, 외부 API를 절대 추가하지 않는다.
2. 단일 HTML 파일 구조를 유지한다. import/export 모듈 문법을 파일 안에 넣지 않는다.
3. 완전 오프라인으로 동작해야 한다. 제로 네트워크 이그레스 원칙을 깨지 않는다.
4. 저작권 표기는 오직 `Copyright (c) 2026 Morgan J. (Gyu-min Jeon) — Licensed under the
   Apache License 2.0` 형식만 사용한다. 다른 이름이나 도구 제작자를 절대 표기하지 않는다.
5. 특정 AI 도구가 코드를 작성했다는 문구를 코드나 주석이나 문서 어디에도 넣지 않는다.
6. 기존 CHANGELOG 주석은 삭제하지 않고 최상단에 누적한다.
7. CSP는 해시 고정 방식이다. `<script>` 또는 `<style>` 블록의 바이트를 한 글자라도
   바꾸면 해당 블록의 SHA-256 해시를 재계산해서 CSP meta 태그에 반드시 다시 써야 한다.
   이 절차를 빠뜨리면 앱이 부팅되지 않는다. (아래 8번 섹션이 이 문제의 근본 해결책이다.)

키보드 동작"을 보강하는 것이므로 인터페이스 변경에 해당하지 않는다. 시각적 결과가
달라지지 않도록 구현한다.

## 2. A1 — 모달 공통 접근성 완성

### 왜 필요한가
현재 파괴적 대화상자는 취소 버튼 기본 포커스와 Enter 처리가 되어 있으나, 모달 공통
컴포넌트 차원의 접근성은 미완성이다. 키보드나 스크린리더 사용자는 모달이 열려도 포커스가
배경에 남거나, 모달을 닫은 뒤 원래 위치로 돌아오지 못한다.

### 현재 상태 (실측)
`inert` 및 포커스 트랩 관련 코드가 사실상 없다. backdrop 클릭 취소만 일부 존재한다.

### 무엇을 구현하는가
모든 오버레이(도움말, 진단, 법적 고지, 마법사, 상세, 언어 선택, 확인 대화상자)에 공통
적용할 모달 접근성 헬퍼를 하나 만든다. 헬퍼는 다음을 수행한다.

1. 모달을 열기 직전에 현재 포커스 요소를 저장한다.
2. 모달 내부의 첫 포커스 가능 요소로 포커스를 옮긴다. 단 파괴적 대화상자는 기존처럼
   취소 버튼에 포커스를 유지한다.
3. 모달이 열려 있는 동안 Tab과 Shift+Tab이 모달 안에서만 순환하도록 트랩한다.
4. 배경 영역에 `inert` 속성을 부여하여 배경 요소가 탭 순서와 스크린리더에서 제외되게 한다.
5. 모달을 닫을 때 저장해 둔 원래 요소로 포커스를 복귀시킨다.
6. Escape 키로 닫힌다. 이미 있는 취소 경로와 동작을 일치시킨다.
7. 중첩 모달은 금지하거나 스택으로 관리한다. 우선은 금지가 단순하고 안전하다.

### 어디를 고치는가
파일 후반부의 새 IIFE 블록 하나로 구현한다. 기존 모달 열기/닫기 함수를 래핑하는 방식이
안전하다. 각 오버레이의 열기 함수(예: 도움말, 진단 등)가 호출될 때 헬퍼의 activate를,
닫기 함수에서 헬퍼의 restore를 호출하도록 연결한다.

### 주의점
- 시각적 변화가 없어야 한다. `inert`는 화면 모양을 바꾸지 않는다.
- `inert`를 지원하지 않는 구형 브라우저를 위해, 미지원 시 배경 요소의 tabindex를 임시로
  -1 처리하는 폴백을 둔다. 폴백 실패가 앱을 멈추게 해서는 안 된다(try/catch로 감싼다).
- Trusted Types 정책과 충돌하지 않도록 DOM 조작은 기존 sanitizer 경로를 따른다.

### 완료 검증
- 각 모달을 열고 Tab을 계속 눌러도 포커스가 배경으로 새지 않는다.
- Escape로 닫으면 모달을 열기 전 눌렀던 버튼으로 포커스가 돌아온다.
- 스크린리더에서 배경 콘텐츠가 읽히지 않는다.

## 3. A2 — 토글·카드·선택 요소의 role과 키보드 지원

### 왜 필요한가
설정의 토글 상당수가 `<div>` 기반이고 `role="switch"`, `tabindex`, `aria-checked`,
Space/Enter 처리가 없다. 키보드 사용자는 토글을 조작할 수 없고 스크린리더는 상태를
읽지 못한다. pet-card, 아이콘 선택, 스캔 후보, 거리 프리셋도 같은 문제를 가진다.

### 현재 상태 (실측)
`role="switch"`와 `aria-checked` 사용이 0건이다.

### 무엇을 구현하는가
1. 토글 요소에 `role="switch"`, `tabindex="0"`, `aria-checked`(현재 상태 반영)를 부여한다.
2. Space와 Enter 키로 토글이 켜지고 꺼지도록 키보드 핸들러를 추가한다. 상태 변경 시
   `aria-checked` 값을 갱신한다.
3. 선택형 요소(pet-card, 아이콘, 스캔 후보, 거리 프리셋)에는 적절한 role(예: 목록은
   `role="listbox"`/`role="option"`, 버튼 성격은 `role="button"`)과 키보드 조작을 부여한다.
4. 기존 클릭 동작과 완전히 동일한 결과를 내야 한다. 키보드 경로는 마우스 경로와 같은
   함수를 호출한다.

### 어디를 고치는가
정적 마크업에 속성을 추가하면 스타일 블록 밖의 HTML이므로 스크립트/스타일 CSP 해시에는
영향이 없다. 다만 마크업 변경도 파일 바이트를 바꾸므로, 만약 변경이 `<style>`나
`<script>` 내부가 아니라면 CSP 해시 재계산은 필요 없다. 키보드 핸들러는 기존 액션
디스패처 방식(`data-vg-on*`)을 그대로 사용해 정책 허용목록 안에서 처리한다.

### 주의점
- 새 액션을 추가하면 반드시 `VitalGuardActionPolicy`의 허용목록(allowed 객체)에 등록한다.
  등록하지 않으면 디스패처가 차단한다. (이는 V4.5.8에서 확인된 정책 동작이다.)
- 시각적 모양은 그대로 두고 속성과 키 동작만 추가한다.

### 완료 검증
- Tab으로 각 토글에 도달하고 Space/Enter로 켜고 끌 수 있다.
- 스크린리더가 토글의 켜짐/꺼짐 상태를 읽는다.
- 최종 DOM의 모든 `data-vg-on*` 액션이 `VitalGuardActionPolicy.parse()`를 통과한다
  (아래 C2의 액션 검증 스크립트로 확인).

## 4. A3 — Toast 및 오류 메시지 aria-live 전달

### 왜 필요한가
Toast와 오류 메시지가 시각적으로만 표시되어 스크린리더 사용자에게 전달되지 않는다.

### 현재 상태 (실측)
`aria-live`, `role="status"`, `role="alert"` 사용이 0건이다.

### 무엇을 구현하는가
1. Toast 컨테이너에 `role="status"`와 `aria-live="polite"`를 부여한다.
2. 오류성 메시지(가져오기 실패, 저장 실패 등)는 `aria-live="assertive"` 또는
   `role="alert"`로 즉시 읽히도록 한다.

### 어디를 고치는가
Toast 모듈의 컨테이너 생성 지점과 오류 표시 지점.

### 완료 검증
- Toast가 뜰 때 스크린리더가 내용을 읽는다.
- 저장 실패 같은 오류가 즉시 안내된다.

## 5. A4 — viewport 확대 차단 해제

### 왜 필요한가
현재 viewport 메타에 `maximum-scale=1.0,user-scalable=no`가 있어 저시력 사용자가 화면을
확대할 수 없다. 이는 접근성 지침에 어긋난다.

### 현재 상태 (실측)
`maximum-scale=1.0,user-scalable=no`가 그대로 존재한다.

### 무엇을 구현하는가
viewport 메타를 `width=device-width,initial-scale=1.0`까지만 남기고 확대 차단 부분을
제거한다.

### 어디를 고치는가
head의 viewport meta 태그.

### 주의점
- 이 태그는 `<script>`/`<style>` 블록 밖이므로 CSP 해시 재계산은 불필요하다.
- 확대를 허용해도 레이아웃이 깨지지 않는지 실제로 확인한다.

### 완료 검증
- 모바일에서 손가락 확대(핀치 줌)가 동작한다.

## 6. B1 — 슬라이더 저장 debounce와 저장 시점 조정

### 왜 필요한가
볼륨과 경계값 슬라이더가 `input` 이벤트마다 저장을 호출한다. 저장 경로는 보관함 전체를
다시 암호화하므로, 저사양 안드로이드에서 슬라이더를 움직이면 쓰기 큐가 밀려 지연이
생긴다.

### 현재 상태 (실측)
`volumeSlider`가 `data-vg-oninput="Settings.setVolume(this.value)"`로 매 input마다
저장한다. 보관함은 단일 봉투를 매번 전체 재암호화한다(아래 B2 참고).

### 무엇을 구현하는가
1. 화면 표시는 즉시 갱신하되, 실제 저장은 200~300ms debounce를 적용한다.
2. 또는 저장 시점을 `change`(또는 pointer 해제) 시점으로 옮긴다.
3. 같은 tick에 발생한 여러 설정 변경은 하나의 저장 트랜잭션으로 묶는다.
4. 저장이 진행 중일 때 들어온 추가 변경은 최신 값 하나로 병합한다.

### 어디를 고치는가
설정 모듈의 setVolume 및 임계값 저장 경로. debounce 유틸을 바닐라 JS로 직접 작성한다
(외부 라이브러리 금지).

### 주의점
- UI 반응성은 그대로 유지해야 한다. 표시는 즉시, 저장만 늦춘다.
- debounce 중 앱이 닫히면 마지막 값이 유실될 수 있으므로, pagehide/visibilitychange
  시점에 대기 중인 저장을 즉시 flush 한다.

### 완료 검증
- 슬라이더를 빠르게 움직여도 저장 호출이 과도하게 반복되지 않는다.
- 슬라이더 조작 후 앱을 닫았다 열어도 마지막 값이 유지된다.

## 7. B2 — 보관함 레코드 단위 암호화 분할

### 왜 필요한가
현재 `SecureVaultV455.atomicUpdate()`는 변경이 있을 때마다 전체 상태를 복제·정규화·
직렬화·AES-GCM 재암호화한다. 음성 클립이 data URL 형태로 같은 상태에 들어가므로, 음성이
저장된 뒤에는 볼륨 같은 작은 변경조차 큰 상태 전체를 반복 암호화하게 된다.

### 현재 상태 (실측)
`atomicUpdate(mutator)`가 단일 봉투(`__vg_vault_v455__`)를 통째로 재암호화한다.
savePet, saveSetting, saveAI, saveBlob 모두 이 경로를 쓴다.

### 무엇을 구현하는가
보관함을 하나의 거대한 암호문 대신 독립 레코드로 나눈다.

- vault metadata (스키마 버전, 인덱스)
- settings envelope
- pet별 envelope (반려동물마다 하나)
- AI state별 envelope
- voice blob envelope (음성마다 하나)

각 레코드에 독립 IV와 AAD를 적용한다. 그러면 작은 설정 변경 시 해당 레코드만 다시
암호화하면 되고, 큰 음성 데이터를 매번 재암호화하지 않아도 된다.

### 어디를 고치는가
`SecureVaultV455` 전체와 이를 호출하는 Store.savePet/deletePet/saveSetting/saveAI/
saveBlob 경로. 가장 난도가 높은 항목이므로 아래 순서를 지킨다.

1. 먼저 기존 단일 봉투를 읽어 레코드 단위로 분해하는 마이그레이션 함수를 만든다.
2. 새 저장 경로를 레코드 단위로 구현한다.
3. 읽기 경로는 레코드들을 모아 기존과 동일한 상태 객체를 복원하도록 한다.
4. 기존 단일 봉투가 있으면 최초 실행 시 자동 마이그레이션하고, 실패 시 기존 봉투를
   보존하여 데이터 손실이 없게 한다(fail-safe).

### 주의점
- 암호 강도(AES-GCM-256, PBKDF2-SHA-256 600,000 iterations, AAD 바인딩)는 낮추지 않는다.
- 단일 배포 파일 원칙과 충돌하지 않는다. 레코드는 IndexedDB/localStorage 안에서 여러
  키로 나뉠 뿐, HTML 파일은 여전히 하나다.
- 마이그레이션 실패가 앱을 멈추거나 데이터를 지워서는 안 된다.

### 완료 검증
- 음성 클립이 저장된 상태에서 볼륨을 바꿔도 음성 데이터가 재암호화되지 않는다(저장
  시간이 크게 줄어드는 것으로 확인).
- 기존 단일 봉투 사용자가 업데이트해도 데이터가 그대로 복원된다.
- 세션 잠금/해제/마이그레이션/용량 초과/손상 상태에서 모두 안전하게 동작한다.

## 8. C1 — 자동 CSP 해시 생성 빌드 절차

### 왜 필요한가
인라인 코드를 편집한 뒤 사람이 손으로 해시를 다시 계산해서 CSP에 넣는 절차는 반드시
다시 실패한다. 실제로 과거에 해시 미갱신으로 앱이 부팅되지 않은 사고가 있었다. 이
절차를 자동화하면 회귀를 구조적으로 차단할 수 있다.

### 현재 상태
해시는 편집 때마다 수동으로 재계산해야 한다. (V4.5.8에서도 수정 후 수동 재계산으로
맞췄다.)

### 무엇을 구현하는가
빌드 단계에서 다음을 자동 수행하는 스크립트를 만든다.

1. 최종 `<script>`와 `<style>` 블록의 정확한 내부 바이트를 추출한다(여는 태그의 `>`
   다음부터 닫는 태그 `</` 직전까지).
2. 각 블록의 base64 SHA-256을 계산한다.
3. CSP meta의 `script-src`/`script-src-elem`와 `style-src`/`style-src-elem`의 해당
   해시 값을 자동으로 교체한다.
4. 교체 후 최종 파일 전체의 SHA-256을 계산해 배포 매니페스트에 기록한다.

참고 계산식(개념): base64로 인코딩한, 블록 내부 텍스트의 SHA-256 다이제스트.

### 주의점
- 이 스크립트는 개발 편의 도구일 뿐, 배포되는 산출물은 여전히 단일 HTML 파일 하나다.
- 배포용 전체 파일 해시는 단순 텍스트보다 서명된 매니페스트로 제공하는 편이 낫다.
  독립된 신뢰 채널로 배포하고, 오프라인에서 검증 가능한 서명 방식을 쓴다.
- HTTP로 서빙할 때는 파일 내부 메타 설명에 그치지 말고 실제 응답 헤더까지 확인한다.
  meta CSP는 frame-ancestors를 강제할 수 없으므로 서버 헤더가 필요하다는 점은 파일에
  이미 고지되어 있다.

### 완료 검증
- 인라인 코드를 한 글자 바꾼 뒤 스크립트를 돌리면 해시가 자동으로 맞춰지고 앱이
  정상 부팅된다.
- 최종 파일 해시가 매니페스트와 일치한다.

## 9. C2 — 최종 산출물 E2E 검증 세트 구축

### 왜 필요한가
정적 감사(문법 통과, 외부 참조 없음, 액션 정의 존재, 언어 키 개수 일치, 해시 일치)는
"정의가 있는가"만 본다. 실제로는 정의가 있어도 파서가 거부하거나, 키가 있어도 후처리가
덮어쓰거나, 엄격한 보안 규칙이 정상 동작을 막는 문제가 생긴다. 릴리스 게이트의 중심을
"최종 브라우저에서 실제로 작동하는가"로 옮겨야 한다.

### 무엇을 구현하는가
다음을 자동 검증하는 테스트 세트를 만든다.

1. 최종 CSP가 적용된 상태에서 정상 부팅되는가.
2. 최종 DOM의 모든 정적·동적 `data-vg-on*` 액션이 실제로 호출 가능한가
   (`VitalGuardActionPolicy.parse()`에 전부 통과하는가). 이것이 V4.5.8에서 발견된
   가져오기 차단 결함을 사전에 잡는 핵심 테스트다.
3. 암호화 백업: 내보내기 → 초기화 → 가져오기 → 데이터 일치 확인.
4. 보관함 상태: session/locked/unlocked/migration/quota/corrupt 각각에서 안전 동작.
5. 7개 언어의 핵심 안전 문구가 실제로 해당 언어로 표시되는가(스냅숏 비교). "키 개수가
   같은가"에 더해 "내용이 실제 그 언어인가"를 본다.
6. 동일 모델 태그 2개 이상 라우팅(V4.5.8에서 수정한 라우팅 순서가 유지되는지 회귀 테스트).
7. 모달 Escape/Enter/Tab/배경 클릭 동작.
8. SOS 길게 누르기 취소(V4.5.8에서 추가한 취소 경로 회귀 테스트).
9. 화면 잠금·백그라운드·복귀.
10. 저장소 용량 부족 상황.
11. 저사양 안드로이드에서 슬라이더와 음성 데이터 성능.

### 어디서 실행하는가
액션 파서 검증(2번)과 문법 검증은 Node로 파일에서 블록을 추출해 검사할 수 있다. 나머지
브라우저 의존 항목은 실제 브라우저 실행이 필요하다.

### 완료 검증
- 위 테스트가 모두 통과한 파일만 배포 후보로 삼는다.
- 하나라도 실패하면 실패 항목을 먼저 고친다.

## 10. D1 — 모듈 소스 분리 후 단일 HTML 자동 번들

### 왜 필요한가
개발 소스가 58만 바이트, 1만 줄이 넘는 단일 파일이며, 이전 구현을 지우지 않고 후속
IIFE가 다시 감싸고 재정의하는 방식이 반복된다. 이 구조에서는 최종적으로 어떤 함수가
실행되는지 코드 위치만으로 판단하기 어렵고, 래퍼 순서에 따라 동작이 바뀌며, 보안 패치가
정상 기능을 막는 회귀가 반복된다(V4.5.8의 가져오기 차단이 그 예다).

### 무엇을 구현하는가
개발 소스를 기능별 모듈로 분리한다.

```
src/
  security/
  storage/
  crypto/
  ble/
  models/
  ui/
  i18n/
  diagnostics/
  tests/
```

릴리스 단계에서만 이들을 하나의 HTML로 번들링한다. 사용자에게는 계속 단일 파일을
제공하면서 내부에는 각 기능의 유일한 권위 있는 구현만 유지한다.

### 주의점
- 최종 배포물은 반드시 단일 HTML 파일이어야 한다. 모듈 분리는 개발 소스에만 적용된다.
- 번들 결과가 기존 동작과 동일함을 C2의 E2E로 반드시 확인한 뒤 전환한다.
- 이 작업은 회귀 위험이 크므로 C1(자동 해시)과 C2(E2E)가 갖춰진 뒤에 착수한다.

### 완료 검증
- 번들된 단일 HTML이 기존과 동일하게 동작하고 E2E를 통과한다.
- 각 기능에 대해 실행되는 구현이 하나뿐임을 코드에서 추적할 수 있다.

## 11. D2 — 죽은 코드와 중복 재바인딩 계층 정리

### 왜 필요한가
같은 기능이 여러 번 감싸지고 재정의되어 죽은 코드가 남아 있다. 테스트가 중간 구현을
검사하고 최종 구현을 놓칠 수 있다.

### 무엇을 정리하는가 (예시 후보)
- 여러 번 감싸지는 App.init
- 여러 번 재정의되는 Diag.snapshot
- 복수의 가져오기 구현
- 복수의 Sanitizer
- 두 개 존재하는 audit hardening 객체
- 과거 버전용 no-op 스텁
- 사용되지 않는 임계값 상수

### 주의점
- 반드시 D1의 모듈 구조 위에서 진행한다. 단일 거대 파일 상태에서 섣불리 지우면
  실행 순서 의존성 때문에 앱이 깨질 수 있다.
- 제거 전후로 C2의 E2E를 돌려 동작이 동일한지 확인한다.

### 완료 검증
- 제거 후에도 모든 E2E가 통과한다.
- 각 기능의 구현이 하나만 남는다.

## 12. 권장 릴리스 순서 (요약)

1. **다음 핫픽스/마이너**: A1, A2, A3, A4(접근성) + B1(슬라이더 debounce). 위험이 낮고
   사용자에게 바로 도움이 된다.
2. **그 다음**: C1(자동 해시), C2(E2E). 구조 개선을 안전하게 하기 위한 토대.
3. **구조 개선**: B2(레코드 단위 암호화), D1(모듈 번들), D2(죽은 코드 정리). C2가
   갖춰진 뒤 진행한다.

각 단계 완료 시 CHANGELOG를 파일 최상단에 누적하고, 변경한 인라인 블록의 CSP 해시를
재계산하며(또는 C1 스크립트로 자동화), 저작권 표기와 AI 도구 무언급 원칙을 다시 확인한다.

## 13. 매 작업 공통 마무리 체크리스트

작업을 마칠 때마다 아래를 확인한다.

- [ ] 외부 라이브러리·CDN·외부 API·fetch가 추가되지 않았다.
- [ ] 단일 HTML 파일 구조가 유지된다.
- [ ] 완전 오프라인으로 동작한다.
- [ ] 저작권 표기가 `Morgan J. (Gyu-min Jeon)` / Apache License 2.0 형식이다.
- [ ] AI 도구가 코드를 작성했다는 문구가 어디에도 없다.
- [ ] CHANGELOG가 최상단에 누적되었고 이전 이력이 삭제되지 않았다.
- [ ] 변경한 `<script>`/`<style>` 블록의 CSP 해시를 재계산해 meta에 반영했다.
- [ ] 새로 추가한 액션은 `VitalGuardActionPolicy` 허용목록에 등록했다.
- [ ] 최종 DOM의 모든 `data-vg-on*` 액션이 파서를 통과한다.
- [ ] UX/인터페이스의 겉모습은 바뀌지 않았다(접근성 속성·키보드 동작만 보강).
- [ ] 두 인라인 스크립트가 문법 오류 없이 파싱된다.
- [ ] 전체 파일 SHA-256을 계산해 배포 매니페스트에 기록했다.
