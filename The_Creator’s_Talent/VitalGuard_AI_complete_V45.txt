0. REVIEWER SUMMARY (English — shareable with OTF Security Lab)
--------------------------------------------------------------------------------
VitalGuard is a single-file, offline-first, zero-dependency HTML/JS application
for surveillance- and censorship-resistance. Its security model is primarily
STRUCTURAL: the most dangerous attack surfaces — network egress, data
exfiltration, server-side attack surface, and transport-layer MITM — are removed
by architecture, not merely mitigated.

V4.5 adds an immutable "hardening core" that runs as the first executable step
and closes six residual client-side surfaces identified in V4.4.1:

  1. WebRTC IP-leak channel  (RTCPeerConnection family neutralised)
  2. Reversible egress stubs (now locked: non-writable + non-configurable)
  3. Worker/SharedWorker egress bypass (constructors neutralised; CSP also blocks)
  4. Prototype pollution     (Object/Array/Function/String/Number/Boolean frozen)
  5. Dynamic code execution  (indirect eval neutralised; CSP already forbids it)
  6. window.name covert channel (kept empty across navigations)

Plus a bounded runtime self-check and a SHA-256 integrity fingerprint for
tamper-evidence.

HONEST SCOPE STATEMENT: No client-side artifact is provably unbreakable, and a
static review — however thorough — is NOT a substitute for an independent
penetration test. This report documents the hardening that was implemented and
verified by inspection. The authoritative validation remains the OTF Security
Lab white-box engagement. Presenting this build as "rigorously hardened with a
documented threat model and known limitations" is both accurate and the posture
most likely to earn auditor confidence.

2. INDEPENDENT WHITE-BOX ANALYSIS (auditor's own review, not skill output)
--------------------------------------------------------------------------------
THREAT MODEL (as built):
  The dominant risk for an offline single-file tool is NOT remote compromise
  (there is no server and no live network), but: (a) covert exfiltration if any
  script executes, (b) client-side code injection, (c) data-at-rest exposure,
  (d) de-anonymisation via browser side channels. V4.5 is organised around
  shrinking exactly these.

WHAT V4.5 GENUINELY IMPROVES OVER V4.4.1:
  + The single highest-value fix is WebRTC removal. In V4.4.1 a crafted or
    injected snippet could instantiate RTCPeerConnection and, via ICE
    candidates, reveal the device's local and public IP even behind VPN/Tor —
    a direct contradiction of the product's purpose. V4.5 makes the constructors
    throw and locks them.
  + Egress immutability matters because V4.4.1's stubs were plain reassignments;
    an attacker with script execution could overwrite window.fetch back to a
    working handle. V4.5's non-configurable/non-writable definitions defeat that
    specific restoration path. (The existing try/catch reassignments in the body
    fail silently against the lock, which is the intended outcome.)
  + Prototype freezing removes the classic __proto__ / constructor.prototype
    pollution sinks at the language level, complementing the action-policy
    string filter that already blocked those tokens.

RESIDUAL RISKS / HONEST LIMITATIONS (these belong in the OTF disclosure):
  R-1  Self-integrity and the runtime self-check are TAMPER-EVIDENCE, not tamper-
       PROOF. An adversary who can already inject script into the page can also
       alter or remove the checker. They raise the cost of silent tampering;
       they do not make the file immutable. State this plainly to reviewers.
  R-2  Several CSP directives (frame-ancestors, sandbox, report-to) are IGNORED
       when CSP is delivered via <meta http-equiv> rather than an HTTP header.
       For clickjacking, the practical control in a header-less single file is
       JS frame-busting; if the file is ever served over HTTP, set the CSP and
       X-Frame-Options as real response headers. Do not claim header-only
       protections that a <meta> tag cannot enforce.
  R-3  Static, in-file CSP nonces are not per-request secrets. In a single
       offline file the nonce is readable by anyone who can read the document,
       so it chiefly blocks naive injected inline scripts; it is not equivalent
       to server-generated nonces. This is acceptable for the offline model but
       should be described accurately.
  R-4  Key-derivation strength is bounded by Web Crypto: PBKDF2 @ 600k is strong
       and standards-aligned, but PBKDF2 is not memory-hard. Argon2/scrypt are
       not natively available without shipping a dependency (which would violate
       the zero-dependency rule). Current choice is the correct trade-off; note
       it rather than overstate it.
  R-5  Browser/runtime trust: all client-side defenses assume an uncompromised
       browser and OS. A rooted device, a malicious browser build, or a
       hardware keylogger is outside any in-page control. This is a property of
       the platform, not a defect of VitalGuard.

DO-NOT-OVERCLAIM GUIDANCE FOR THE OTF CONVERSATION:
  - Lead with the threat model and the architectural elimination of egress.
  - Present the six V4.5 fixes as defense-in-depth, each independently useful.
  - Disclose R-1..R-5 proactively. Auditors trust teams that surface their own
    limitations far more than teams that claim impenetrability.
  - Avoid absolute words ("unbreakable", "impenetrable") in any written or
    spoken statement to the Lab.
